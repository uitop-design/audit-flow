# AuditFlow — API Design

Status: **Phase 0 proposal**. Swagger generated from the code becomes the authoritative reference
once implemented. This document is the design contract it must satisfy.

## 1. Conventions

| Topic           | Convention                                                                                                                        |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Base path       | `/api/v1` (global prefix `api` + Nest URI versioning)                                                                             |
| Format          | JSON only, `Content-Type: application/json`; field names in `camelCase`                                                           |
| Timestamps      | ISO 8601 UTC with milliseconds, e.g. `2026-11-05T14:03:22.418Z`                                                                   |
| IDs             | UUID (v7, generated by PostgreSQL)                                                                                                |
| Single resource | Returned as a plain object                                                                                                        |
| Collections     | `{ "data": [...], "meta": { page, limit, total, totalPages } }`                                                                   |
| Errors          | Uniform error body (§7)                                                                                                           |
| Request ID      | `X-Request-Id` accepted (if it matches `^[A-Za-z0-9._-]{1,128}$`) or generated; always echoed in the response and in error bodies |
| Docs            | Swagger UI at `/api/docs`, OpenAPI JSON at `/api/docs-json`                                                                       |
| Auth            | **None in MVP.** All endpoints assume a trusted network (see §9)                                                                  |

Audit events are immutable. **No `PUT`, `PATCH` or `DELETE` exists for audit events.** Requests with those
methods get the standard 404 because no route matches.

## 2. Resource: AuditEvent

```json
{
  "id": "019a5a3c-7e2b-7c41-9f0e-3b8d2a6c1f44",
  "eventType": "USER",
  "action": "USER_UPDATED",
  "resourceType": "USER",
  "resourceId": "usr_123",
  "actorId": "usr_456",
  "actorEmail": "admin@example.com",
  "actorName": "John Doe",
  "description": "Updated user permissions",
  "metadata": { "source": "admin-dashboard" },
  "before": { "role": "USER" },
  "after": { "role": "ADMIN" },
  "ipAddress": "127.0.0.1",
  "userAgent": "Mozilla/5.0",
  "correlationId": "req_abc123",
  "source": "example-app",
  "createdAt": "2026-11-05T14:03:22.418Z"
}
```

Every field is always present in responses. Optional values are `null`, never omitted, so clients
don't need to handle two "missing" states. `metadata` is always an object (`{}` when not provided).

## 3. `POST /api/v1/audit-events` — record an event

### Request body

| Field           | Type           | Required | Rules                                                                   |
| --------------- | -------------- | -------- | ----------------------------------------------------------------------- |
| `eventType`     | string         | yes      | `^[A-Z][A-Z0-9_]*$`, 1–64 chars                                         |
| `action`        | string         | yes      | `^[A-Z][A-Z0-9_]*$`, 1–100 chars                                        |
| `resourceType`  | string         | yes      | `^[A-Z][A-Z0-9_]*$`, 1–64 chars                                         |
| `resourceId`    | string \| null | no       | trimmed, 1–255 chars                                                    |
| `actorId`       | string \| null | no       | trimmed, 1–255 chars                                                    |
| `actorEmail`    | string \| null | no       | valid email, ≤ 320 chars                                                |
| `actorName`     | string \| null | no       | trimmed, 1–200 chars                                                    |
| `description`   | string         | yes      | trimmed, 1–1000 chars                                                   |
| `metadata`      | object         | no       | JSON **object** (not array/primitive); serialized ≤ 16 KB; default `{}` |
| `before`        | object \| null | no       | JSON object; serialized ≤ 32 KB; default `null`                         |
| `after`         | object \| null | no       | JSON object; serialized ≤ 32 KB; default `null`                         |
| `ipAddress`     | string \| null | no       | valid IPv4 or IPv6                                                      |
| `userAgent`     | string \| null | no       | ≤ 512 chars                                                             |
| `correlationId` | string \| null | no       | `^[A-Za-z0-9._:-]+$`, 1–128 chars                                       |
| `source`        | string         | yes      | `^[a-z0-9][a-z0-9._-]*$`, 1–100 chars (e.g. `billing-service`)          |

Rules that apply to the whole body:

- **Unknown properties are rejected** (400). This includes `id` and `createdAt`: the server assigns
  both and never accepts client values.
- Strings are trimmed before validation, and a whitespace-only required string is invalid.
- Whole request body is limited to **128 KB** (413 above that).
- Values are stored as sent (after trimming). They are not HTML-escaped. Consumers must render them safely.

### Responses

| Status                      | When                                                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `201 Created`               | Event stored. Body = AuditEvent. `Location: /api/v1/audit-events/{id}` header                              |
| `400 Bad Request`           | Validation failed: malformed JSON, missing or invalid fields, unknown properties, JSON too large per field |
| `413 Payload Too Large`     | Body exceeds 128 KB                                                                                        |
| `500 Internal Server Error` | Unexpected failure (generic message only)                                                                  |

Example:

```bash
curl -i -X POST http://localhost:3000/api/v1/audit-events \
  -H 'Content-Type: application/json' \
  -d '{
    "eventType": "USER",
    "action": "USER_UPDATED",
    "resourceType": "USER",
    "resourceId": "usr_123",
    "actorId": "usr_456",
    "actorEmail": "admin@example.com",
    "actorName": "John Doe",
    "description": "Updated user permissions",
    "metadata": { "source": "admin-dashboard" },
    "before": { "role": "USER" },
    "after": { "role": "ADMIN" },
    "ipAddress": "127.0.0.1",
    "userAgent": "Mozilla/5.0",
    "correlationId": "req_abc123",
    "source": "example-app"
  }'
```

_Idempotency:_ the MVP has none, so a retried POST creates a second event. An `Idempotency-Key`
header backed by a unique column is the documented extension point.

## 4. `GET /api/v1/audit-events` — list events

### Query parameters

| Param           | Type              | Default     | Rules                                                                                                                                                                           |
| --------------- | ----------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `page`          | integer           | `1`         | ≥ 1                                                                                                                                                                             |
| `limit`         | integer           | `20`        | 1–100                                                                                                                                                                           |
| `search`        | string            | —           | trimmed, 1–200 chars; case-insensitive substring over `description`, `actorEmail`, `actorName`, `actorId`, `resourceId`, `action`, `correlationId`; `%` and `_` match literally |
| `eventType`     | string            | —           | exact match                                                                                                                                                                     |
| `action`        | string            | —           | exact match                                                                                                                                                                     |
| `resourceType`  | string            | —           | exact match                                                                                                                                                                     |
| `resourceId`    | string            | —           | exact match                                                                                                                                                                     |
| `actorId`       | string            | —           | exact match                                                                                                                                                                     |
| `source`        | string            | —           | exact match                                                                                                                                                                     |
| `correlationId` | string            | —           | exact match (addition to the brief's list; backed by an index, used for "show related events")                                                                                  |
| `dateFrom`      | ISO 8601 datetime | —           | inclusive lower bound on `createdAt`                                                                                                                                            |
| `dateTo`        | ISO 8601 datetime | —           | **exclusive** upper bound; must be after `dateFrom`                                                                                                                             |
| `sortBy`        | enum              | `createdAt` | `createdAt` \| `eventType` \| `action` \| `resourceType` \| `actorEmail` \| `source`                                                                                            |
| `sortOrder`     | enum              | `desc`      | `asc` \| `desc`                                                                                                                                                                 |

- All filters combine with AND.
- Unknown query parameters are rejected with 400, so a typo such as `eventtype=` can't silently
  return unfiltered data.
- A `sortBy` outside the whitelist is a 400, never passed to the database.
- Results always get a secondary sort on `id` in the same direction, so ordering stays stable across pages.
- A `page` past the last page returns `200` with empty `data` and accurate `meta`.
- Dates use a half-open interval `[dateFrom, dateTo)`. To filter "all of 5 November" in the UI, the web
  app sends `dateFrom=<local start of Nov 5>` and `dateTo=<local start of Nov 6>`, both converted to UTC.

### Response `200 OK`

```json
{
  "data": [{ "id": "…", "eventType": "AUTH", "action": "USER_SIGNED_IN", "...": "…" }],
  "meta": { "page": 1, "limit": 20, "total": 150, "totalPages": 8 }
}
```

`totalPages` is `0` when `total` is `0`.

Example:

```bash
curl 'http://localhost:3000/api/v1/audit-events?eventType=PERMISSION&dateFrom=2026-11-01T00:00:00Z&sortBy=createdAt&sortOrder=desc&limit=50'
```

## 5. `GET /api/v1/audit-events/{id}` — get one event

| Status            | When                     |
| ----------------- | ------------------------ |
| `200 OK`          | Body = AuditEvent        |
| `400 Bad Request` | `id` is not a valid UUID |
| `404 Not Found`   | No event with that id    |

## 6. Supporting read endpoints

These two endpoints were not named in the brief. They are needed so the dashboard shows real data
without the frontend computing aggregates over full result sets, which would break "server-side" and
"don't load everything into memory". Both are read-only and live in the audit-events module.
They are declared before `/{id}` so the static path segments take precedence.

### `GET /api/v1/audit-events/stats`

```json
{
  "totalEvents": 184,
  "eventsLast24h": 23,
  "uniqueActors": 14,
  "topEventType": { "eventType": "AUTH", "count": 52 },
  "byEventType": [{ "eventType": "AUTH", "count": 52 }, { "eventType": "PROJECT", "count": 38 }],
  "dailyVolume": [{ "date": "2026-10-23", "count": 9 }, { "date": "2026-11-05", "count": 23 }],
  "recentEvents": [{ "...": "AuditEvent (5 most recent)" }],
  "generatedAt": "2026-11-05T14:05:00.000Z"
}
```

- `uniqueActors` = count of distinct non-null `actorId`. Events without an `actorId`, such as system
  actions, are not counted.
- `topEventType` is `null` when there are no events. `byEventType` is sorted by count descending.
- `dailyVolume` covers the last 14 UTC days, zero-filled, so the chart has a stable x-axis.
- `eventsLast24h` is relative to the database's `now()`.

### `GET /api/v1/audit-events/facets`

Distinct values for filter dropdowns, sorted alphabetically:

```json
{
  "eventTypes": ["API_KEY", "AUTH", "PERMISSION", "PROJECT", "USER"],
  "actions": ["API_KEY_CREATED", "API_KEY_REVOKED", "PROJECT_CREATED", "..."],
  "resourceTypes": ["API_KEY", "PROJECT", "USER"],
  "sources": ["admin-dashboard", "billing-service", "web-app"]
}
```

Each list is capped (500 values) as a guard against unbounded growth. At larger cardinality this would
move to a typeahead endpoint.

## 7. `GET /api/v1/health`

| Status                    | Body                                                                                                                       |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `200 OK`                  | `{ "status": "ok", "checks": { "database": { "status": "up", "latencyMs": 2 } }, "uptimeSeconds": 512, "timestamp": "…" }` |
| `503 Service Unavailable` | `{ "status": "error", "checks": { "database": { "status": "down" } }, … }`, with no connection details                     |

## 8. Error format

All errors, including validation, 404, 413 and unexpected 500s, use one shape:

```json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Request validation failed",
  "details": [
    { "field": "actorEmail", "message": "actorEmail must be an email" },
    { "field": "createdAt", "message": "property createdAt should not exist" }
  ],
  "path": "/api/v1/audit-events",
  "requestId": "6f1c2b9e-…",
  "timestamp": "2026-11-05T14:03:22.418Z"
}
```

- `details` appears only for validation errors.
- 500 responses always say `"message": "Internal server error"`. The real error is logged server-side
  with the `requestId` and is never returned.
- Prisma "record not found" and connectivity errors are translated to domain/HTTP errors, and Prisma
  codes never reach the client.

| Status | Used for                                                                               |
| ------ | -------------------------------------------------------------------------------------- |
| 200    | Successful reads                                                                       |
| 201    | Event created                                                                          |
| 400    | Validation errors, malformed JSON, invalid UUID, unknown params/fields, bad sort field |
| 404    | Event not found; unknown route (including mutation verbs on audit events)              |
| 413    | Request body over the limit                                                            |
| 500    | Unexpected server errors                                                               |
| 503    | Health check when the database is unreachable                                          |

## 9. Security notes for consumers

- **The ingestion endpoint must not be exposed to the public internet in its MVP form.** Before
  production, put it behind service-to-service authentication (mTLS, signed tokens or API keys) and
  rate limiting. Protect read endpoints with operator authentication and role-based access.
- Treat everything in an audit event as potentially sensitive. Producers should not send secrets,
  tokens or full payment data in `metadata`/`before`/`after`, and should redact at the source.
- CORS is restricted to `CORS_ORIGINS`. Server-to-server producers are unaffected by CORS.
